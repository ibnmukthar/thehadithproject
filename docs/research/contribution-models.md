# How open-knowledge projects let non-technical contributors add structured data under expert review — survey and recommendation for thehadithproject.com

Sources fetched 2026-10-23. Pages that blocked fetching are flagged; Europeana was not surveyed.

## 1. Git-backed editing for non-technical users

**Decap CMS (ex-Netlify CMS)** — `publish_mode: editorial_workflow` maps editor actions to git: "Save draft: Commits to a new branch (named `cms/collectionName/entrySlug`), and opens a pull request"; each save adds a commit; "Approve and publish" merges and deletes the branch. Works with GitHub, GitLab (status via MR labels) and Bitbucket (via PR comments); `squash_merges: true` collapses each entry to one commit. https://decapcms.org/docs/editorial-workflows/
Auth: the GitHub backend "allows CMS users to log in directly with their GitHub account" and "all users must have push access to your content repository"; GitHub OAuth needs a server (Netlify, self-hosted proxy, or Decap Turbo). https://decapcms.org/docs/github-backend/ https://decapcms.org/docs/backends-overview/
**Open Authoring** removes the write-access requirement: "the CMS forks your repository for them behind the scenes"; board shrinks to Draft / Ready to Review; contributor sees only own changes; maintainers merge on GitHub; GitHub backend only; "Open Authoring users cannot publish entries through the CMS." Contributors still need a GitHub account. https://decapcms.org/docs/open-authoring/
**Git Gateway + Netlify Identity** is the only path where editors "don't need to know about GitHub or create a GitHub account" — but Netlify deprecated Identity/GoTrue on 28 Feb 2025 and a Feb 2026 community post reports a reversal; shaky foundation. https://decapcms.org/docs/git-gateway-backend/ https://netlify.com/changelog/deprecation-netlify-identity https://github.com/decaporg/decap-cms/discussions/7419
Rendered review: `registerPreviewTemplate` renders an entry in a preview pane next to the form so editors/reviewers see the page, not YAML. https://decapcms.org/docs/customization/

**TinaCMS** (Tina Cloud) — saving to a protected branch prompts for a branch name, "creates the branch, indexes its content, saves the changes, and opens a draft pull request"; publish = merge on GitHub. Editors are Tina Cloud users (owner connects GitHub once). Editorial Workflow is "only available on the Business and Enterprise plans." https://tina.io/docs/drafts/editorial-workflow/ https://tina.io/editorial-workflow

**Keystatic** (GitHub mode) — login via a custom GitHub App; "Collaborators will need `write` access to this repository"; admin UI has a branch dropdown and `branchPrefix`; PRs are opened on GitHub from the branch (shown in a tutorial, not in docs); no draft/review states. https://keystatic.com/docs/github-mode https://egghead.io/lessons/react-manually-connect-a-keystatic-project-to-a-github-repo

**Sveltia CMS** — Decap rewrite; secondhand reports say it works on a single branch with editorial workflow still pending; its roadmap/docs pages for "Editorial Workflow" and "Open Authoring" returned 404 at fetch time. Not ready for a review workflow. https://github.com/sveltia/sveltia-cms https://sveltiacms.app/en/docs/roadmap

**GitHub itself** — web editor: "When you edit a file in another user's repository, we'll automatically fork the repository and open a pull request for you" (Edit → Propose changes → Create pull request); requires a GitHub account. https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files
Issue forms: YAML templates with typed `input`/`textarea`/`dropdown`/`checkboxes`, `required: true`; "responses for each input are converted to markdown and added to the body of an issue." Also needs an account. https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms
Rendering for reviewers: CSV/TSV files render "as an interactive table" in file view; prose gets a rich diff; CSV *diffs* are plain text. https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files
Attribution without accounts: `Co-authored-by: NAME <EMAIL>` trailers record name+email in the commit; linking to a profile only happens if the email is on a GitHub account. https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/creating-a-commit-with-multiple-authors
Bots: a GitHub App exchanges a JWT for a 1-hour installation token scoped to repos/permissions; "API requests made by an app installation are attributed to the app." https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation
Previews: Cloudflare Pages gives every PR/branch a preview URL that updates per commit, but "Previews are only created for pull requests that originate from the repository itself, not from forks" — so a bot must push branches into the main repo, not forks. https://developers.cloudflare.com/pages/configuration/preview-deployments/

## 2. Structured-data crowdsourcing with validation

**Wikidata** — unit: a statement (property + value + qualifiers + reference) on an item; anyone may edit. Property constraints "are hints, not firm restrictions"; violation reports show on item pages for logged-in users and in Special:ConstraintReport. Patrolling: "usually available to all (auto-)confirmed users"; edits of confirmed users are auto-patrolled; four steps (identify → fix/remove → warn → check other edits). Audit: full per-item revision history with summaries. https://www.wikidata.org/wiki/Help:Property_constraints_portal https://www.wikidata.org/wiki/Wikidata:Patrol

**OpenStreetMap** — unit: a changeset ("a collection of elements edited by a mapper in a single editing session") with comment, user, timestamp; public changeset discussion; element history links each version to its changeset. iD is the default in-browser editor (78% of mappers in 2024) with an integrated issue/validation manager; saving needs an OSM account. Notes: "it is not necessary to be logged in to submit a new note"; resolved notes are kept. Data Working Group handles "serious disputes and vandalism", reverts, 96-hour blocks, redactions; routine vandalism is left to the community. https://wiki.openstreetmap.org/wiki/Changeset https://wiki.openstreetmap.org/wiki/ID https://wiki.openstreetmap.org/wiki/Notes https://wiki.openstreetmap.org/wiki/Data_working_group

**Zooniverse** — unit: one task (question/drawing/transcription) on one subject; account optional ("you do not need to create an account… your answers will still be saved") but anonymous work is unattributable. Builder sets a retirement limit per workflow: suggested 10–20 generally, "3 or 5" for full-text transcription (Galaxy Zoo used 40; Planet Hunters 8/10/15 adaptive). "Zooniverse does not currently offer aggregated classifications for text subjects" — teams reconcile offline or in ALICE, where team members see "an automatically-generated aggregate transcription for each line" plus every submitted version, edit, and export. Talk boards: one thread per subject. Audit: classification exports (user/anon id, timestamp), ALICE edits. https://help.zooniverse.org/getting-started/ https://www.zooniverse.org/projects/krwood/old-weather-ww2/about/faq https://arxiv.org/pdf/1903.07776 https://help.zooniverse.org/next-steps/integrations/ https://www.bpl.org/blogs/post/anti-slavery-manuscripts-final-project-update/

**Wikisource** — unit: a page; statuses Not proofread / Problematic / Proofread (one contributor) / Validated (two) / Without text; "you cannot both proofread and validate the same page"; IP editors cannot set status; colour-coded index. Audit: page history. https://en.wikisource.org/wiki/Help:Page_status
**FromThePage** — page statuses; owner chooses optional vs required review; reviewers open "Pages That Need Review", compare to scan, "Approve"; review does not lock; UI "shows you the users who were working on it." https://content.fromthepage.com/project-owner-documentation/reviewing-in-fromthepage/ https://github.com/benwbrum/fromthepage/wiki/Understanding-Page-Statuses
**Transkribus** — New → In Progress (automatic) → Done / Final / Ground Truth (manual, colour-coded); meanings are team-defined. https://blog.transkribus.org/en/how-to-train-a-text-recognition-model-in-transkribus https://rechtsprechung-im-ostseeraum.archiv.uni-greifswald.de/category/transkribus-in-practice/first-steps/

**iNaturalist** — unit: an identification on an observation. Research Grade when the observation is Verifiable (date, coordinates, media, wild) and "more than 2/3 of identifiers agree on a taxon at species-level" (or family-to-species plus a vote that it is "as good as it can be") and community taxon = observation taxon; otherwise Needs ID; Casual if DQA votes fail. Community taxon = lowest taxon scoring >2/3 with ≥2 IDs. Every ID is a timestamped, attributed record. https://help.inaturalist.org/support/solutions/articles/151000169936 https://gbif.org/dataset/50c9509d-22c7-4a22-a47d-8c48425ef4a7

**Smithsonian Transcription Center** — anyone (anonymous) transcribes and "Save"s; "Submit for Review"; the reviewer must be a registered, *different* user who returns or completes the page; completed pages become public/searchable. No per-page staff sign-off found. https://transcription.si.edu/instructions/begin https://transcription.si.edu/faqs https://nmaahc.si.edu/explore/initiatives/smithsonian-transcription-center

## 3. Scholarly review models

**Wikipedia Pending Changes** — on protected pages, edits by unregistered/new users "are saved, but are marked as pending changes"; readers see the last accepted revision; reviewer checks are "a quick check… obviously inappropriate content"; "acceptance… is not to be considered an endorsement"; history shows "accepted by [Username]" and a review log. https://en.wikipedia.org/wiki/Wikipedia:Pending_changes
**FlaggedRevs / German "gesichtete Versionen"** — editor/reviewer groups with `review`, `autoreview`, `validate` rights; "All relevant actions are permanently logged" (Special:Log/review). German WP: sighting means "free of obvious vandalism" and "does not state that the article has been checked for subject-matter accuracy"; Sichter status is automatic after thresholds (e.g. 60 days, 300 edits, <3% reverted). MediaWiki itself calls the extension "complex, poorly documented… not recommended for production use." Lesson: keep "patrolled" and "scholar-approved" as different statuses. https://www.mediawiki.org/wiki/Extension:FlaggedRevs https://de.wikipedia.org/wiki/Wikipedia:Gesichtete_Versionen
**OpenReview** — "configurable platform… generalizes over many subtle gradations of openness"; venues set forms, read/write access and timing; ICLR allows public author–reviewer discussion; nonprofit, AGPL. https://openreview.net/about https://ICLR.cc/archive/www/doku.php%3Fid=iclr2017:faq.html
**Pleiades** — drafting (owner-only) → "submits" for review (locks edits; editors can send back) → editor publishes. Edits to published records go through a checked-out working copy; "While a working copy is being edited and reviewed, the baseline resource is locked"; check-in yields "a new, authoritative, published version." Contributor is credited under "Creators"/"Contributors" on the record and on the Credits page; a Reviewers' Guide exists; review backlog hit ~1,000 in 2014. https://pleiades.stoa.org/help/workflow https://pleiades.stoa.org/help/add-a-new-name-resource https://pleiades.stoa.org/news/blog/review-parties-in-december-and-january
**Syriaca.org** — per-record TEI titleStmt lists named contributors with roles ("editorial oversight", "text entry", "proofreading"); editorial principles require citations; adopting Perseids for editorial review (blog fetch failed: connection refused). https://syriaca.org/person/279.xml https://syriaca.org/persons https://blog.syriaca.org/2018/08/8212018-perseids-user-summit-presentation-syriaca-org-and-perseids-editorial-review/
**Papyri.info / SoSOL (Papyrological Editor)** — the closest analogue. Storage: "A single 'canonical' repository holds public, approved data. Each user and board has its own repository, acting as a fork of the canonical one"; git gives "fully-auditable version control." Workflow (Perseids/Tufts instructions, same software): contributor edits in Leiden+, runs "Find Error", previews, writes a commentary, submits; board members (assigned by admin) see pending items flagged red, open Preview / History / Comments, vote **Approve or Reject with a comment**; "Once the required number of Approve votes are received, the publication moves to the finalization stage"; a finalizer may make final edits, then "add a comment and click Finalize to commit the changes." Rejections return to the submitter; "rejected proposals are not deleted forever, and are instead retained in the digital record"; board comments are visible on the public text page ("See All comments"); guiding principle "permanent transparency." Data is on GitHub (idp.data, CC BY 3.0), syncs hourly both ways with the editor; PRs accepted only for batch changes "case by case"; GitHub Issues for data problems. A reviewer with no DH training reports that "classicists (and others) without training in the sphere of Digital Humanities can contribute." https://github.com/sosol/sosol https://sites.tufts.edu/perseusupdates/?p=47 https://blog.stoa.org/archives/4163 https://github.com/papyri/idp.data https://papyri.info/docs/about (bot wall at fetch time)

## 4. Islamic-studies correction channels

- **sunnah.com** — open-source corrections ingestor (Flask): "receives corrections (with an API key) at https://corrections.sunnah.com/submit" as JSON `{urn, attr, val, lang, comment, queue, submittedBy}`; the site's report link feeds it. No public review trail; `data` repo is "ad hoc scripts", no licence; site returned 403 to fetch. https://github.com/sunnah-com/corrections https://github.com/sunnah-com
- **QUL – Quranic Universal Library (Tarteel)** — the best Islamic-studies model: CMS where "each resource type has its own editing and review workflow" and "Contributions are reviewed before they are published"; proofreading tools for translations, tafsir, mushaf layouts (Approved 20 / WIP 8); access via "Send Access Request" per tool; corrections also via GitHub issue; per-resource licences; contributors credited. https://qul.tarteel.ai/docs/contribute-data https://qul.tarteel.ai/faq https://qul.tarteel.ai/ https://qul.tarteel.ai/credits
- **Quran.com** — Translation Feedback (Jan 2026): ayah menu → choose translation → submit; system "Links your report to the selected surah and ayah… Tracks its status"; partnered providers get reports forwarded, others "remain under review within our system"; plus feedback.quran.com board. https://quran.com/product-updates/new-translation-feedback-feature https://feedback.quran.com/translation-and-tafsir-errors/p/ibn-kathir-eng-surah-jinn-verse-1
- **Tarteel** — help articles for reporting Quran text/tashkeel/translation errors; public board feedback.tarteel.ai. https://support.tarteel.ai/en/collections/15105282-troubleshooting-and-support https://feedback.tarteel.ai/bugs/p/bug-report-ayah-recognition-issue-surah-as-saffat-ayah-36
- **OpenITI/KITAB** — every Author/Title/Version cell in the metadata search links to a GitHub issue form ("you'll need a GitHub account"); corrections target fidelity to the print edition; `UNCORRECTED_OCR` tags; volunteer curators. https://kitab-project.org/The-New-OpenITI-Metadata-Search/ https://kitab-project.org/openiti-curators-session1/
- **IHSAN / Thesaurus Islamicus** — closed, ~100 scholars, registration-only database, commercial editions; no public contribution path. https://hcommons.org/groups/ihsn https://fonsvitae.com/product/the-sunna-project-thesaurus-islamicus-foundation/
- **Jawami al-Kalim** — no public corrections channel found. The de-facto hadith-app pattern is a Canny-style board (GTAF): user posts typo, staff reply "fixed on the server" — no public diff. https://feedback.gtaf.org/hadith/p/many-typos-in-a-hadith-riyad-as-salihin-1866

## Recommended architecture for thehadithproject.com

Goal: a web portal that turns volunteer work into reviewed pull requests in the public repo, with a named scholar's sign-off written into each record, and a "report a correction" link on every line — none of which requires contributors to touch git or hold a GitHub account.

**1. Keep git as the sole public record; keep work-in-progress in a database.** SoSOL's split is the right one: raw submissions, votes and drafts live in the portal DB; only reviewed results are committed. Use Cloudflare Workers + D1 (SQLite) for submissions/tasks, R2 for scan crops, Turnstile for anti-spam — all already on your deploy stack.

**2. Contributor identity without GitHub.** Portal login by email magic-link or Google (e.g. Better Auth or Lucia-style library on Workers, or hosted Auth0/Clerk). Contributors give a display name and a contact email they consent to publish; the portal writes `Co-authored-by: Name <email>` trailers so attribution survives in git even without GitHub accounts. Anonymous *reports* allowed (OSM Notes), anonymous *edits* not (Wikisource/Smithsonian).

**3. Git writer = a GitHub App.** A Worker holds the App key, mints a 1-hour installation token scoped to `contents` + `pull_requests`, and uses the Git Data API to create a branch `portal/<task>/<record-id>` *in the main repo* (not a fork, so Cloudflare Pages preview deployments work), commit the changed YAML/JSON record(s), and open a PR whose body is templated: task type, evidence (scan crop URL, edition/page), every submission considered, and the reviewer's decision. Label by task type.

**4. Review happens in the portal, not in a JSON diff.** The reviewer screen shows the rendered record (same components as the live site), old/new side by side, the scan, and all independent submissions (ALICE-style). On approval the portal (a) writes a `review` block into the record file — `reviewer_id`, reviewer's public profile/ORCID, role, date, decision, note, base commit — and (b) posts a PR review via the App naming the reviewer. A GitHub Actions check (JSON Schema via ajv + a "sign-off present and reviewer is on the editorial-board list" check) plus branch protection makes merge impossible without it; if scholars do have GitHub accounts, add CODEOWNERS on `data/**` requiring the reviewers team. Optionally the portal signs the review block (Ed25519) so sign-offs verify offline. Two distinct statuses, learned from FlaggedRevs: `validated` (matches source, any trained volunteer) vs `approved` (named scholar).

**5. "Report a correction" on every line.** Each rendered line/field links to `/correct?record=…&field=…&line=…`, prefilled with current value; form asks for proposed value, reason, source (edition/page or URL), optional email. No login; Turnstile. The Worker stores it in D1 *and* mirrors it as a GitHub Issue through the App (public, auditable, like OpenITI/idp.data) with a structured body modelled on issue forms. A maintainer triages into a task; the eventual PR references the issue and credits the reporter if they opted in. A public `/reports` page shows status (Quran.com's "tracks its status", but visible).

**6. Publish the raw layer too.** Periodically commit anonymised exports of submissions/votes under `contributions/` (Zooniverse classification exports) so the "two transcriptions disagreed, reviewer chose X" reasoning is in the open record, and keep rejected proposals (SoSOL: "retained in the digital record").

**Named tools:** Cloudflare Pages/Workers/D1/R2/Turnstile; GitHub App + Octokit (`@octokit/app`); GitHub Actions + ajv; branch protection + CODEOWNERS; Cloudflare Pages preview deployments; `Co-authored-by` trailers.

**Trade-offs / alternatives considered**
- *Decap CMS editorial workflow*: cheapest to stand up and a good fit for the *editorial board's own* record editing (one entry = one PR, preview pane), but contributors need GitHub accounts (or the Netlify Identity/Git Gateway path, deprecated Feb 2025 then reportedly reinstated), Open Authoring PRs don't appear on editors' board, and there is no multi-submission consensus. Reasonable phase-1 for staff; not for the public.
- *TinaCMS*: polished but PR workflow is a paid Business/Enterprise feature on a proprietary cloud. *Keystatic*: editors need repo write access; no review states. *Sveltia*: single-branch today.
- *Self-hosting SoSOL/Perseids*: conceptually the closest (per-user git forks, boards with vote thresholds, finalizer), but a JRuby/Rails stack built around EpiDoc/Leiden+; adapting it costs more than building the thin portal above.
- *Zooniverse Project Builder* for the transcription stage only: free, mature retirement/Talk machinery, but no built-in text aggregation and results still need an offline → PR step; RTL/Arabic input would need testing.
- *A Wikibase instance*: excellent constraints/history, but a second system of record beside git with sync headaches.

## Micro-task designs

| Task | UI | Independent submissions before review | Who signs off |
|---|---|---|---|
| Transcribe a Taqrib entry from a scan | Scan crop above a single RTL text field with diacritics palette; optional structured fields (name, kunya, nisba, grade, death date) in a *second* pass once the line is validated | 2 blind transcriptions; auto-`validated` if identical after normalising hamza/ta marbuta/diacritics; else a 3rd transcriber, then a validator adjudicates ALICE-style seeing all versions (Zooniverse "3 or 5" for text; Wikisource second-person rule) | Validator (Arabic-literate volunteer, must differ from transcribers); no scholar needed for transcription fidelity |
| Link a chain name to a narrator record (disambiguation) | Show isnad position, name as written, teacher/student neighbours; candidates from the narrator index with death dates, known teachers/students, nisbas; choices: candidate / "new narrator" / "unsure" + note | 3 independent linkers (iNaturalist pattern): 3/3 → `validated` automatically; 2/3 → reviewer decides; split or any "new narrator" → scholar queue | Trained reviewer for consensus; named hadith scholar for contested or new records |
| Enter a scholar's verdict with page reference | Form: scholar, work, edition, volume, page, verbatim quote, scan crop upload, verdict term from controlled list, free note | 1 entry + 1 independent *verifier* who re-reads the cited page and confirms quote and page (Pleiades-style check before publish) | Named editorial-board scholar approves attribution and interpretation; sign-off written into the record |
| Propose a correction to a line | Prefilled report form from the line (record, field, current value), proposed value, reason, source, optional email; no login | 1 report → triage → becomes one of the tasks above (or a maintainer's direct PR for typos, still reviewed) | Maintainer triages; final sign-off follows the task's rule above; reporter credited via `Co-authored-by` if opted in |
